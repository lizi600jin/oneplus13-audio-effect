# 一加13 扬声器音效模块 · 实现方案

本文说明这个模块**怎么实现的**，以及如何基于它做自己的音频模块。
包含三部分：硬件实测依据（第三节）、实现架构与机制、调参方法论与踩坑点。

---

## 一、为什么不用 APK

Android 的 `AudioEffect` 生命周期**绑定在持有它的进程上**。进程退出，effect 立刻被系统销毁。

| 方案 | 界面 | 常驻 | 复杂度 |
|---|---|---|---|
| APK + 前台服务 | 需要 | 需要（还要防杀） | 高：签名、通知栏权限、保活 |
| **app_process 跑 dex** | 不需要 | 需要 | **低：脚本一行拉起** |
| 改 /vendor 音效库 | 不需要 | 不需要 | 极高，且 erofs 只读 |

本模块采用第二种：`app_process` 以 root 身份执行 dex 的 `main()`，
不需要 APK、不需要签名、不占通知栏，卸载模块即完全清除。

## 二、整体结构

```
┌──────────────────────────────────────────────┐
│ KernelSU / Magisk 模块                        │
│   service.sh → 等 boot_completed + 25s        │
│              → app_process 拉起 spk-eq.dex    │
└────────────────────┬─────────────────────────┘
                     │
┌────────────────────▼─────────────────────────┐
│ DynEqService（常驻 Java 进程）                 │
│   每 200ms 读一次配置                          │
│   内容有变化 → release 旧 effect → 建新 effect │
└────────────────────┬─────────────────────────┘
                     │
┌────────────────────▼─────────────────────────┐
│ DynamicsProcessing（系统音效）                  │
│ AudioEffect 挂 session 0 = 全局混音输出        │
│ 所有 App 的声音都经过它                         │
└──────────────────────────────────────────────┘
```

**`session 0` 是全局输出**：`new DynamicsProcessing(0, 0, config)`
第一个 0 是 priority，第二个 0 是 sessionId。sessionId 传 0 表示挂全局混音，
而不是某个播放器实例。

## 三、硬件实测：默认曲线的依据

默认曲线不是拖滑块试出来的。以下三条是直接从设备上量到的硬件事实，
曲线是照它们设计的。

### 3.1 两颗喇叭的出厂衰减量不同

一加13 用两颗 AW88461 功放，分别推上扬（顶部）和下扬（底部）。
寄存器 `0x05` 的低 10 位是**衰减量**，出厂值：

| 喇叭 | 寄存器读回 | 低 10 位 |
|---|---|---|
| 上扬 | `0xc040` | 64 |
| 下扬 | `0xc030` | 48 |

读法（root）：

```bash
B=/sys/devices/platform/soc/9c0000.qcom,qupv3_i2c_geni_se/990000.i2c/i2c-4
echo "0x05" > $B/4-0034/rw && cat $B/4-0034/rw   # 上扬
echo "0x05" > $B/4-0035/rw && cat $B/4-0035/rw   # 下扬
```

### 3.2 这个数字越小，声音越大

```
0    → 最大
48   → 原厂下扬
64   → 原厂上扬
1023 → 完全静音
```

验证方法：把某侧拉到 1023，那颗喇叭会**彻底不响**，只剩另一颗在发声。
这是听出来的，不是推出来的。方向搞反会把喇叭越调越小。

### 3.3 喇叭谐振点 f0 = 714~758 Hz

芯片可以直读 f0：

```bash
cat $B/4-0034/f0_show    # pri_l:758pri_r:714
```

714~758 Hz 正好夹在**人声基频下沿**与**低频乐器基频上沿**之间，
两边能量在这里互相掩蔽 —— 这就是「糊」「杂糅」的物理来源。

**推论：只拉高低频会更糊。** 拉的是 200 Hz，掩蔽发生在 700 Hz，
基底抬得越高，掩蔽区相对就被压得越不明显，但能量冲突本身没解决。

### 3.4 实测结论如何落到曲线上

| 实测 | 曲线处理 |
|---|---|
| f0 714~758 Hz 是掩蔽区 | 削 469~750 Hz（−7 dB） |
| 削完偏薄 | 补 200 Hz 冲击、补 1.2~3.6 kHz 人声主体 |
| 中高频留空隙会「脱节」 | 4500 Hz 补 1 dB 衔接 |
| 齿音在 5~9 kHz | 抬 8115 Hz 亮度，5.6 kHz 稍压防刺 |

> 注意：本模块**不写功放寄存器**。上面这些实测只用于决定 EQ 曲线怎么画。
> 直接改寄存器也能调音量，但那是另一条路（需要开机脚本或改 ACF，
> 且两颗喇叭的 ACF 各自独立，风险更高）。

## 四、为什么选 DynamicsProcessing 而不是 Equalizer

| | `Equalizer` | `DynamicsProcessing` |
|---|---|---|
| 频段数 | 固定 5 | 最多 14（可配） |
| 频点 | 固定 60/230/910/3600/14000 Hz | 任意 |
| Q 值 | 不可调 | 无此参数（机制不同） |
| 动态处理 | 无 | MBC + limiter |
| 增益范围 | ±15 dB | 实测 ±9 可用 |

5 段 EQ 的最低频点 60Hz 与手机喇叭谐振（714~758Hz）严重错配，
调 230Hz 会整带全抬，结果是「糊」。所以换可编程的 10 段。

## 五、DynamicsProcessing 的真实工作机制

**它不是在时域叠加多个钟形滤波器。**

走的是 **FFT 频域分段常数**：

```cpp
// AOSP frameworks/av/media/libeffects/dynamicsproc/dsp/DPFrequency.cpp
bp.binStop = (int)(0.5 + bp.freqCutoffHz * mBlockSize / mSamplingRate);

// 每段覆盖 [上一段 binStop+1, 本段 binStop] 的连续 bin
for (size_t k = bp.binStart; k <= bp.binStop; k++)
    cb.mPreEqFactorVector[k] = factor * inputGainFactor;   // 整段同一常数
```

即：**把频谱切成连续块，每块乘一个固定增益。块与块之间是硬跳变，没有过渡。**

### blockSize 的来源

```cpp
// EffectDynamicsProcessing.cpp
int32_t desiredBlock = mPreferredFrameDuration * samplingRate / 1000.0f;
int32_t currentBlock = powerof2(desiredBlock)
        ? desiredBlock
        : (1 << (32 - __builtin_clz(desiredBlock)));
```

Java 侧默认 `CONFIG_PREFERRED_FRAME_DURATION_MS = 10.0f`：

```
48000 Hz × 10 ms ÷ 1000 = 480 采样
480 不是 2 的幂 → 向上取 512
→ mBlockSize = 512，每个 bin = 48000 ÷ 512 = 93.75 Hz
```

**最小可控带宽 = 93.75 Hz。** 需要更细的分辨率要改 `setPreferredFrameDuration`
（数值越小频率分辨率越高，但延迟增大）。

## 六、配置文件格式

### `/data/adb/spk-eq/conf` —— EQ 曲线（必需）

每行 `频率Hz:增益dB`，最多 14 行，空行与 `#` 开头忽略。

```conf
200:7
420:1
650:-7
1200:1
2400:4
3600:5
4500:1
5500:-1
8115:6
20000:2
```

规则：
- 频点严格递增（代码会自动排序去重）
- 最后一段从它的频点一直覆盖到 Nyquist（24000 Hz）
- 全部为 0 → 自动旁路，不创建 effect

### `/data/adb/spk-eq/mbc` —— 多段压缩（可选）

每行 `频率Hz:阈值dB:压缩比:启动ms:释放ms`，最多 14 行。
文件为空或不存在 = 关闭 MBC。

```conf
220:-18:4:8:90
800:-22:4:8:90
3000:-24:4:6:70
8000:-26:3:5:60
```

作用：让各频段**独立动态**工作——响的频段自动压、轻的频段浮现。
EQ 是静态曲线，治不了「糊」；MBC 可以改善分离度。

### `/data/adb/spk-eq/limiter` —— 限幅器（可选）

单个数字，单位 dB。不存在时默认 `-1`。写 `-99` = 完全关闭。

## 七、源码结构

```
src/
└── DynEqService.java     主服务：读配置 → 建 effect → 循环监听
```

关键成员：

| 位置 | 作用 |
|---|---|
| `CONF` / `LOG` 常量 | 配置与日志路径 |
| `parse()` | 读 conf，插排排序、去重 |
| `build()` | 构造 `DynamicsProcessing`，写入各段参数 |
| `main()` | 无限循环，200ms 轮询，签名变化则重建 |

### 两个必须注意的实现约束

**约束 1：band 数量必须等于实际频段数**

```java
int bands = Math.max(1, Math.min(MAXB, n));   // 不能用固定 MAXB
```

固定建 14 个 band 而只填 10 个，剩余会被填成默认频点 `40*2^i`，
频点序列变成 `... 8115, 20000, 2560, 5120 ...` —— **非单调**。
`DynamicsProcessing` 要求严格递增，非单调会让滤波器系数算错，
整个 EQ 输出不可信（表现为「提亮反而变闷」）。

**约束 2：MbcBand 构造器是 11 个参数**

```java
// (enabled, cutoff, attack, release, ratio, threshold,
//  kneeWidth, noiseGate, expanderRatio, preGain, postGain)
new DynamicsProcessing.MbcBand(true, m[0], m[3], m[4], m[2], m[1],
                               0f, -60f, 1f, 0f, 0f)
```

写成 8 个参数会编译报「找不到合适的构造器」。

## 八、编译与部署

```bash
# 1. 编译（必须用 SDK 的 android.jar）
AJ=~/.local/opt/android-sdk/platforms/android-36/android.jar
javac --release 17 -cp "$AJ" -d out src/DynEqService.java

# 2. 转 dex
d8 --min-api 30 --output out out/DynEqService.class

# 3. 推到设备
adb push out/classes.dex /data/adb/spk-eq/dyn.dex

# 4. 重启服务
adb shell su -c "ps -A -o PID,ARGS | grep app_process | grep -i DynEq \
  | grep -v grep | awk '{print \$1}' | xargs -r kill -9"
adb shell su -c "cd /data/adb/spk-eq && nohup sh -c \
  'CLASSPATH=/data/adb/spk-eq/dyn.dex app_process /system/bin DynEqService' \
  > /data/local/tmp/spkeq.out 2>&1 &"
```

**注意：设备上的 `framework.jar` 只有兼容性 XML，没有 classes，不能当 classpath。**
必须用 Android SDK 的 `android.jar`。

## 十、调参方法论

**不要靠公式推算，靠 ABAB 盲听。**

```
1. 生成固定测试素材（粉红噪声或扫频，30~60 秒）
2. 脚本按 A B A B 段序切换（A=原厂，B=待测曲线），每段 8~10 秒
3. 听的时候不知道当前是哪一段
4. 听到明显好听/难听的段落，记下时间点
5. 对照答案键，判断是 A 还是 B
```

用 ABAB 而不是 AB，是为了抵消随时间的漂移（注意力、耳压、环境温度）。

**为什么主观试听比算曲线可靠：**

- 「糊」「暖」「刺」「脱节」这些判断是主观的，但真实可复现
- 曲线的绝对 dB 值不重要，**相对差异**才决定听感
- 同样的参数换到另一个喇叭上效果完全不同，公式算不出来

一次只改一个变量。同时改多个频点，听感变化无法归因。

### 10.1 先标定「听得出」的最小幅度

盲听之前必须先知道：**多大的改动才听得出来**。否则要么改太小听不出白忙，
要么改太大直接过冲。

做法是准备同一条曲线按倍数缩放，中间插原厂做参照：

```
×1   220:+2.5  542:-1.5  3293:+1.5  8115:+2.0
×2   220:+5.0  542:-3.0  3293:+3.0  8115:+4.0
×3   220:+7.5  542:-4.5  3293:+4.5  8115:+6.0
×4   220:+10   542:-6.0  3293:+6.0  8115:+8.0
```

一加13 扬声器上的实测结果：

| 档位 | 结果 |
|---|---|
| ×1 | **听不出** |
| ×2 | 听出来了 |
| ×3 以上 | 差异明显 |

**结论：在手机扬声器上，±2 dB 量级的调整基本无感，要 ±4 dB 才可靠可闻。**
这条规律决定了后面所有曲线的调整步长——起步就是 4~7 dB，不做小步微调。

### 10.2 用「功能描述」判断，不用「好听」判断

纯凭「好听/不好听」打分会陷入选择困难（多档都好听，无法收敛）。
更有效的是让试听者描述**具体差异**：

- 「低频鼓点更实」
- 「人声和伴奏分开了」
- 「中间一段变扁了」
- 「像两头翘」
- 「中频和中高频之间缺一段」

**带功能描述的反馈才可归因**。例如「缺一段」直接指向频谱上的空隙，
可以据此定位到具体缺哪个频段；而「好听」无法指向任何参数。

### 10.3 交叉验证：不告诉顺序

切回原厂时，对方应该能**自发识别出**「变扁了 / 声音小了」。
如果切了原厂却毫无察觉，说明当前改动幅度不足，或者判断只是心理作用。

## 十一、制作自己的模块（最小骨架）

```bash
mkdir -p my-module

# module.prop
cat > my-module/module.prop <<'EOF'
id=my_audio_mod
name=我的音效模块
version=v1.0
versionCode=100
author=你的名字
description=一句话说明
EOF

# customize.sh —— 建配置目录
cat > my-module/customize.sh <<'EOF'
#!/system/bin/sh
SKIPUNZIP=0
mkdir -p /data/adb/my-audio
[ -f /data/adb/my-audio/conf ] || echo "200:5" > /data/adb/my-audio/conf
set_perm_recursive "$MODPATH" 0 0 0755 0644
EOF

# service.sh —— 开机拉起
cat > my-module/service.sh <<'EOF'
#!/system/bin/sh
MODDIR=${0%/*}
i=0
while [ "$(getprop sys.boot_completed)" != "1" ] && [ $i -lt 120 ]; do
  sleep 1; i=$((i+1))
done
sleep 25
nohup sh -c "CLASSPATH=$MODDIR/engine.dex app_process /system/bin MyService" \
  > /dev/null 2>&1 &
EOF

# 打包（module.prop 在根目录）
cd my-module && zip -r ../my-module.zip ./*
```

要换成自己的处理逻辑，只需修改 `DynEqService.java` 中 `build()` 那段。

## 十二、已知限制

| 限制 | 说明 |
|---|---|
| 只作用于全局输出 | 无法针对单个 App |
| 存在处理延迟 | FFT 分帧，约 10ms + 缓冲 |
| 段间硬边界 | 极端参数下可能出现瞬态毛刺 |
| 93.75 Hz 分辨率 | 更细需改 `setPreferredFrameDuration` |
| 依赖进程存活 | 极端内存压力下可能被回收 |
| 不处理采样率转换 | 属于另一层（SRC bypass）的范畴 |
| 与其他音效模块互斥 | session 0 只能挂一个 AudioEffect |
